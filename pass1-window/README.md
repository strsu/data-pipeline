# Pass-1 슬라이딩 윈도우 실험 — 앞뒤 컷 맥락 주입 (2026-07-16)

바바리안(웹툰 23) **10화**에서, Stage V(Pass-1) 비전 콜에 **앞뒤 컷 이미지를 함께** 넣으면
qwen-base(9B)의 품질이 오르는지 측정한다. 출력 계약은 프로덕션과 **완전 동일** — 달라지는 건
입력 프롬프트뿐이다.

## 가설

| 대상 | 기대 | 근거 |
|---|---|---|
| **화자 귀속·인물 동일성** | 개선 | 지금 약한 부분(ep10 CCIP 43%, qwen 단독 34% — `face-classify-w23-2026-07-16.md`). 앞뒤 컷에 대화 순서·같은 인물이 보이면 꼬리가 애매한 말풍선을 문맥으로 풀 수 있다 |
| **블록 1:1 구조(병합/누락)** | **개선 기대 없음** — 악화 여부만 감시 | greedy에서도 모달로 나오는 모델 용량/습관 문제(`pass1-bench-w23-2026-07-16.md`). 오히려 이미지가 늘면 "옆 컷 글자를 blocks에 끌어오는" 신종 오염 위험 |

즉 **주 지표 = 화자, 안전 지표 = 1:1 구조**다.

## 설계 결정

**center-predict.** 창 안의 5장 전부를 예측시키지 않는다. 컷 `T`에 대해 `[T-2 … T … T+2]`를 넣고
**출력은 T 하나만**. 창을 한 칸씩 밀면 모든 컷이 정확히 한 번 타겟이 되므로 출력 병합 정책
(다수결·confidence 가중 등)이 아예 필요 없고, 컨텍스트 효과와 앙상블 효과가 섞이지 않는다.
가장자리는 클리핑(창이 3~4장으로 작아짐) — 타겟을 항상 실제 이웃 사이에 둔다. `window.target_position`을
기록하므로 위치 편향은 사후에 확인 가능(`report`의 `by_target_position`).

**입력은 `datasets/pass1/78c51d18a1d9/`를 재활용.** 그 JSONL에 컷별 오버레이 이미지(모델이 실제로
본 것)·프로덕션 입력(`user_text`)·glm-4.6v 티처 결과·qwen 싱글 결과가 전부 들어있다. 덕분에
(a) DB를 안 붙고, (b) 입력 파리티가 자동 보장되며, (c) **싱글 이미지 베이스라인 콜을 다시 안 해도 된다**.

**컨텍스트 컷은 이미지 + 평문 텍스트, F 라벨은 뺀다.** 컨텍스트의 OCR은 `index` 없는 평문으로
주고(프로덕션 `ocr_blocks` 포맷과 일부러 다르게 — blocks에 끌어다 쓰지 않게), 얼굴은 F 라벨 없이
이름만 준다. F 라벨은 컷마다 독립 번호라 그대로 넘기면 타겟 라벨과 충돌한다(프롬프트 규칙 W3).

**마커 인터리빙 → 직접 호출.** `call_llm_json`은 (텍스트 1개 + 이미지 전부 뒤에 몰기) 구조라 어느
이미지가 몇 번 컷인지 표시할 자리가 없다. 이미지 앞에 `[컷 N] (CONTEXT|TARGET)` 텍스트를 끼우려고
`_call_direct`로 직접 스트리밍 호출한다(멀티이미지 컷 혼동 방어).

**프롬프트.** 프로덕션 `_PASS1_SYSTEM_PROMPT`의 **첫 문장(입력=이미지 1장)만 교체**하고 나머지
규칙(1:1 바인딩, 분류→화자 2단계, 스키마)은 글자 그대로 유지 + `[윈도우 규칙] W1~W4` 추가.
프로덕션 헤더가 바뀌면 즉시 실패하게 해뒀다(drift 방지).

## 사전 실측 — 토큰은 문제가 아니었다

| 항목 | 값 |
|---|---|
| 싱글 이미지 prompt_tokens (ep10, 95컷) | 평균 **1,528** / 최대 1,641 |
| → 오버레이 이미지 1장(1280px 상한) | **≈ 1.3k 토큰** |
| 윈도우 5장 실측 prompt_tokens | **≈ 4,200** (가장자리 3~4장 포함 스모크) |
| qwen-base 컨텍스트 | 64k — **한참 여유** |
| 레이턴시 | 싱글 10.5s → 윈도우 12.3s (**거의 동일**) |

이미지를 더 늘릴 여지도 크다(`--radius 4` → 9장도 ~12k).

## ep10 베이스라인 (이미 있음 — 재활용)

유효 컷 **95개**(전체 107 중 빈컷/이미지없음 12 스킵).

| 방식 | 병합 위반 | index 누락 | 비고 |
|---|---|---|---|
| qwen-base 싱글 | 38컷 (40%) | 45컷 (47%) | 이걸 이겨야(혹은 최소한 안 나빠져야) |
| glm-4.6v 티처 | 0컷 | 0컷 | 화자 일치율의 비교 기준 |

⚠️ **화자 "정확도"가 아니라 glm 티처 대비 "일치율"이다.** ep10에 사람이 확정한 건 *얼굴 정체*이지
*블록별 화자*가 아니라서, 화자에는 사람 정답이 없다. 게다가 티처도 무결하지 않다(qwen이 옳고 glm이
틀린 사례가 실측된 바 있음). 그러니 일치율은 **정답률이 아니라 분포 차이**로 읽어야 한다.

## 실행

```bash
cd webtoon-pipeline && set -a && source ../prod.env && set +a

# 실험(백그라운드 권장, resume 안전 — 기록된 cut_number는 스킵)
PYTHONPATH=. .venv/bin/python ../pass1-window/run_window.py --webtoon 23 --episodes 10
# 스모크 3컷
PYTHONPATH=. .venv/bin/python ../pass1-window/run_window.py --webtoon 23 --episodes 10 --limit 3
# 집계만(콜 없음)
PYTHONPATH=. .venv/bin/python ../pass1-window/run_window.py --webtoon 23 --episodes 10 --report

# 실시간 뷰어 (이미지까지 자체 서빙 — 별도 http.server 불필요)
PYTHONPATH=. .venv/bin/python ../pass1-window/serve.py --port 8791   # → http://127.0.0.1:8791
```

주요 플래그: `--radius 2`(창 5장), `--model qwen-base`, `--workers 1`(로컬 9B 과부하 방지).

**뷰어**: 상단에 병합률·누락률·화자 일치율의 `싱글 → 윈도우` 델타가 5초마다 갱신되고, 아래는 컷마다
`[이미지 | glm 티처 | qwen 싱글 | qwen 윈도우]` 4열 대조. "화자 다른 컷만" 필터가 이 실험의 핵심 뷰다.
